# Rust AED 企画書

## プロジェクト名

**Rust AED (Agentic Document Extraction)**

---

## 1. エグゼクティブサマリー

### 背景

従来の OCR ソリューションには以下の課題があります：

- **Tesseract/PaddleOCR**: 日本語縦書きの精度が低い（約50%）
- **YomiToku**: Python + CUDA GPU が必須で環境構築が困難
- **Google Cloud Vision**: 高精度だが従量課金で高コスト

一方、Anthropic Claude の Vision API は：

- 高い日本語認識精度
- レイアウト・文脈理解能力
- 構造化データ出力対応
- GPU 不要（API ベース）

### 提案

**Claude Vision API を活用した Rust 製 OCR ライブラリ**を開発し、以下を実現します：

1. 日本語縦書きテキストの高精度抽出
2. 構造化データ（JSON）の直接出力
3. 純 Rust 実装による環境依存の排除
4. superbook-pdf との統合

## 2. 目的と目標

### 目的

日本語ドキュメント処理における OCR の民主化

### 定量目標

| 指標 | 目標値 | 計測方法 |
|------|--------|---------|
| 縦書き認識精度 | 95%以上 | 文字単位正答率 |
| 処理速度 | 3秒/ページ以下 | A4文書基準 |
| API コスト | $5/1000ページ以下 | Sonnet 4.5使用時 |
| ライブラリサイズ | 10MB以下 | リリースビルド |

### 定性目標

- Rust エコシステムへの貢献
- 日本語 OCR の選択肢拡充
- superbook-pdf の機能強化

## 3. ターゲットユーザー

### 主要ターゲット

| ユーザー | ニーズ | 提供価値 |
|---------|--------|---------|
| **Rust 開発者** | Python 依存なしの OCR | 純 Rust 実装 |
| **書籍電子化** | 縦書き対応 | プリセット提供 |
| **業務システム** | 請求書・帳票処理 | 構造化抽出 |
| **個人開発者** | 手軽な OCR | シンプル API |

### ペルソナ

**ペルソナ A: サーバーサイド Rust 開発者**

- Python 環境構築を避けたい
- 非同期処理に対応した OCR が欲しい
- AWS Lambda / Cloud Run でデプロイしたい

**ペルソナ B: 電子書籍コンバーター開発者**

- 縦書き日本語書籍を OCR したい
- ルビ（振り仮名）も抽出したい
- バッチ処理で大量ページを処理したい

└──────────────────┘     └────────┬─────────┘

                    ▼                           ▼

## 7. コスト分析

### API コスト

| モデル | 入力コスト | 1000ページあたり |
|--------|-----------|-----------------|
| Claude Sonnet 4.5 | $3/1M tokens | 約 $4.80 |
| Claude Haiku | $0.25/1M tokens | 約 $0.40 |

※ 1ページ ≈ 1,600 tokens として計算

### 比較

| ソリューション | 1000ページコスト | 備考 |
|---------------|-----------------|------|
| **Rust AED (Sonnet)** | $4.80 | 高精度 |
| **Rust AED (Haiku)** | $0.40 | 高速・低コスト |
| Google Cloud Vision | $1.50 | 従量課金 |
| YomiToku (GPU) | 電力代のみ | GPU必須 |

## 8. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| API レート制限 | 大量処理の阻害 | バッチ処理、リトライ実装 |
| 縦書き精度不足 | 品質低下 | プロンプト改善、フォールバック |
| API 料金高騰 | コスト増加 | Haiku モデル選択、キャッシュ |
| オフライン不可 | 利用制限 | ローカル OCR とのハイブリッド |
